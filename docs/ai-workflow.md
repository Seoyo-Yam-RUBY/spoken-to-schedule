# 一、简要说明

## 它是什么

一个把**口语碎片**变成**日程表**的工具。

你说一句「下周三下午三点跟老王对方案」，它把这句话拆成时间、地点、人物，排到时间轴上。说几句就有几条，最后导出 `.ics`，双击进手机日历。

它要解决的是一段很短的路径：从"说出口"到"排进日历"。中间原本要经过备忘录、日历 App、逐条手填，大多数人走不完这三步。

## 技术形态

| 维度 | 选择 | 原因 |
|---|---|---|
| 架构 | 纯静态 | 没有后端就没有账号、没有运维、没有密钥托管 |
| 依赖 | 零 | 不装包、不构建，`git push` 即上线 |
| 数据 | 浏览器 `localStorage` | 数据不出本机 |
| 部署 | GitHub Pages | 免费、稳定、地址固定 |
| 体量 | 4 个文件，约 1200 行 JS | 一个人两天能读完 |

## 做出了什么

| 能力 | 说明 |
|---|---|
| 语音输入 | 点一下开始、再点一下结束；也支持打字 |
| 多事件拆分 | 一句话里几件事，按标点切句后自动归并成多条 |
| 字段解析 | 事件、日期、时刻、时长、人物、地点、是否截止 |
| 双引擎 | 默认本地规则（离线可用）；填 Key 后可走大模型 |
| 类别着色 | 面试蓝、笔试绿、截止红，自动识别，可手动改 |
| 冲突提示 | 顶部斜纹 + 卡间提示行，不改变卡片配色 |
| 结果自检 | 命中可疑条件时标「待确认」，点一下看原因 |
| 就地编辑 | 标题、时间、地点、人物、类别、类型都能改 |
| 导出日历 | `.ics`，带 UID 与 SEQUENCE |
| 失败兜底 | 语音不可用时提示系统听写；模型不可用时回退规则 |

## 它明确不做

- 不做账号与多人协作：数据在各自浏览器里
- 不做实时同步：导出是一次性快照
- 不做自动猜模糊时间：「看情况」一律进「待定」

# 二、工作流

## 2.1 核心判断

AI 在这个项目里不是"写代码的"，而是**造验证手段的**。

代码写得快不快不是瓶颈，**判断对不对**才是。所以整套流程围绕一个目标设计：

> 让每一个"我以为对了"的环节，都变成一个可以立刻执行的检查。

## 2.2 六个阶段

```
① 需求收敛      用一页纸把"要解决什么"钉死
② 数据契约      先定义中间格式，再写任何界面
③ 可运行骨架    第一天就要有能打开的页面
④ 功能迭代      一条验收标准 → 一次提交
⑤ 调试          先复现，再修复；修复即回归
⑥ 交付          构建号、边界说明、演示脚本
```

### ① 需求收敛：一页纸

动手前只回答四个问题，写不满一页就不开工：

- 谁在什么场景下遇到什么问题
- 现在他们怎么凑合
- 这版只解决哪一段
- **明确不做什么**

“不做什么”是这张纸上最重要的一行。它决定了后面所有取舍有依据。

### ② 数据契约：先定格式

所有功能都挂在一个中间格式上：

```json
{
  "title": "对方案",
  "date": "2026-11-18",
  "start": "15:00",
  "duration": 60,
  "people": ["老王"],
  "place": "3楼会议室",
  "kind": "event",
  "category": "interview",
  "confidence": 0.92
}
```

排序、查冲突、着色、导出，全部只是对这张表做运算。

**为什么先定它**：格式一旦稳定，界面、解析、导出可以并行改，互不牵连。反过来，先写界面后定格式，改一次要动三处。

### ③ 可运行骨架：第一天就能点开

先让它跑起来，再让它变好。

顺序固定为：脚手架 → 假数据打通端到端 → 再填真实逻辑。第一天的目标不是"功能"，是"浏览器里能点开"。

部署也放在第一天：空壳先上线，之后每次 `git push` 只验证内容，不再赌管道。

### ④ 功能迭代：一条验收标准一次提交

每个功能都按同一个循环：

```
写验收标准 → 让 AI 实现 → 自己验一遍 → 一次提交
```

提交粒度控制在"能单独回滚"：解析、着色、冲突、导出各自独立。

### ⑤ 调试：复现优先于修复

这是整套流程里最花时间的部分，也是最需要设计的部分。

**原则一：先写复现脚本，再改代码。**
不写复现脚本的修复等于赌博——你不知道自己是修好了，还是恰好绕开了。项目里的复现手段：

- 无头浏览器加载真实页面
- 用 iframe 驱动 DOM：填输入框、点按钮、读 `localStorage`
- 把断言写在脚本里，一条命令跑完

**原则二：一次只动一个变量。**
怀疑输入里有不可见字符时，构造三个变体同时跑：

```
正常文本        明天下午4点到6点
零宽字符变体    明\u200b天\u200b下\u200b午4点到6点
空格变体        明 天 下 午 4 点 到 6 点
```

三个一起跑，哪个出问题一眼可见。人手工试要十分钟，脚本一秒。

**原则三：一行断言换一次回归。**
每个修过的 bug 都变成一条永久用例。项目维护着 10 条句子的回归集，改任何解析逻辑前后各跑一遍。

**原则四：结果不合逻辑时，先怀疑环境。**

| 怀疑对象 | 检查方式 |
|---|---|
| 浏览器缓存 | 无痕窗口打开 |
| 不可见字符 | 逐字打印码点 |
| 全角/半角 | 对比两种写法 |
| 时区 | 打印 `new Date()` 实际值 |
| 客户端差异 | 同一操作换浏览器 |

项目里两个最耗时的 bug 都属于这一类：**页面跑的是缓存里的旧脚本**、**字符串里夹了零宽字符**。逻辑全对，环境不对。

### ⑥ 交付：让"哪一版"可回答

纯静态项目最容易出的交付事故是"我改了，但你看的还是旧的"。三个措施：

1. 静态资源带版本号：`app.js?v=20261111m`
2. 页脚显示构建号，且**由脚本写入**（HTML 新、JS 旧时不会骗人）
3. 每次改动一条提交，提交信息写清"改了什么、为什么"

## 2.3 人与 AI 的分工

| 环节 | AI 做 | 人做 | 为什么 |
|---|---|---|---|
| 需求 | 追问、补漏、写成结构化文档 | **决定做什么、不做什么** | 取舍依赖真实场景 |
| 数据契约 | 起草字段、给示例 | 确认字段够不够用 | 只有人知道后面要什么 |
| 实现 | 出代码、出样式 | 验收、抽查边界 | AI 会"看起来对" |
| 测试 | 生成用例、写断言脚本 | **确认期望值** | 期望是价值判断 |
| 调试 | 复现脚本、假设清单、对照实验 | 判断哪个假设值得先查 | 搜索方向决定效率 |
| 文档 | 起草、改写、压缩 | 定语气、定取舍 | 读者是谁只有人知道 |

一句话：**AI 负责"生成可验证的东西"，人负责"判断什么值得验证"。**

## 2.4 为什么问题点还得人来报

"发现问题"需要两样东西，AI 都不具备：

| 类型 | 例子 | AI 能否自动发现 |
|---|---|---|
| 可判定的问题 | 报错、断言失败、元素缺失 | 能 |
| 需要判据的问题 | 「下午五点」被解析成 05:00 | **不能**，得先有人定义"什么算对" |
| 无法观测的问题 | 麦克风里说了什么、网络谁掐断 | **不能**，信息不在它能拿到的地方 |

判据一旦给出，AI 可以并行跑一万条。所以人的介入不是"每发现一个 bug 报一次"，而是**一次性把判据写下来**。

这也是项目里加「待确认」自检的原因：让 AI 至少能发现"看起来不对劲"，把人的注意力集中到真正可疑的少数几条上。

## 2.5 一个完整的调试案例

**现象**：语音说几句，输入框里前面的话会被"删掉"。

1. **先复现**：用 iframe 驱动真实页面，模拟连续两段语音，稳定复现
2. **提出假设**：`resultIndex` 是"本次新增片段"的起点，而代码从它开始拼接再整体赋值——前面的内容被覆盖
3. **验证**：改成从 0 重建整段，重跑同一脚本，问题消失
4. **回归**：把"连续两段语音"写进检查脚本
5. **记录**：提交信息写清"continuous 模式下 resultIndex 只指向新增片段"

这个链条里，AI 快在 ②③（写脚本、改代码），慢在 ①（知道"这不对劲"）——而 ① 正是人提供的。

# 三、提示词

提示词是**发给 AI 的指令**，不是给人填的表。

## 3.1 一条好提示词的五个部分

| 成分 | 作用 | 例子 |
|---|---|---|
| 角色/任务 | 让它知道在干什么 | “把用户的一段口语整理成日程” |
| 上下文 | 给它判断依据 | “今天是 2026-11-11，时区 Asia/Shanghai” |
| 约束 | 堵住它容易犯的错 | “下午五点 = 17:00，绝不允许写成 05:00” |
| 输出格式 | 让结果可被程序消费 | 固定 JSON schema |
| 示例 | 一次示范胜过十句解释 | 一句话 → 一条 JSON |

判断一段提示词是否合格，标准很简单：**换一个人拿去用，产出的东西形态一样吗？**

变量用 `{{双花括号}}` 标注，每次调用时替换。

## 3.2 解析提示词（项目实际在用）

要点：**先把"今天"写死进提示词**，否则相对时间必错。

```text
今天是 {{TODAY}}（{{WEEKDAY}}），时区 Asia/Shanghai。
把用户的一段口语整理成日程，只输出 JSON，不要解释，不要 markdown 代码块。

硬性规则：
1. date 必须是 YYYY-MM-DD。出现「今天/明天/后天/大后天/这周X/下周X/月底/下月N号」时，
   一律基于今天换算成具体日期，不允许留空。
2. start 必须是 24 小时制 HH:mm。「下午/傍晚/晚上」一律加 12 小时：
   下午五点 = 17:00，绝不允许写成 05:00。
3. 「X 点到 Y 点」表示时间段：start 取 X，duration_min = (Y - X) * 60。
4. 只有原文完全没提日期时 date 才为空；只有完全没提时刻时 start 才为空。
5. kind：「截止/之前完成/最晚」类为 deadline，其余为 event。
6. title 用动词短语，不超过 12 字，不包含时间、地点、人名。
7. 不编造原文没有的信息。
8. category：提到「面试」为 interview，提到「笔试/机试/测评」为 exam，其余为 other。
9. 如果一段话包含多件互不相关的事，events 数组里返回多个对象，不要合并成一条。

示例：
口语：明天下午五点钟有个会
今天是 {{TODAY}}，所以明天是 {{TOMORROW}}，输出：
{"events":[{"title":"开会","date":"{{TOMORROW}}","start":"17:00",
"duration_min":60,"people":[],"place":"","kind":"event","confidence":0.95}]}
```

配套的输出结构（Gemini 用 `responseSchema`，OpenAI 兼容接口用 `json_object`）：

```json
{
  "events": [
    {
      "title": "string",
      "date": "YYYY-MM-DD 或空字符串",
      "start": "HH:mm 或空字符串",
      "duration_min": 0,
      "people": ["string"],
      "place": "string",
      "kind": "event | deadline",
      "category": "interview | exam | other",
      "confidence": 0.0
    }
  ]
}
```

**为什么这几条是硬性的**：模型默认会把「下午五点」写成 05:00、会把相对时间留空、会把多件事合并。这三条必须显式禁止，否则输出看起来合理但全是错的。

## 3.3 需求追问

用在想法还模糊的时候。关键是**只让 AI 提问，不让它给方案**——方案给早了，会把你带偏。

```text
你是产品顾问。我有一个还很模糊的想法：{{一句话想法}}。

约束：
- 只提问，不要给方案，不要评价
- 一次最多问三个问题，按重要性排序
- 每个问题都必须能改变方案的范围或取舍
- 先问场景和人，不要问技术选型

输出：
1. 三个问题
2. 每个问题后面补一句：如果答 A 会怎么做，如果答 B 会怎么改
```

## 3.4 实现任务

关键在**先要计划、再要代码**，以及把验收标准写成可观察的行为。

```text
任务：{{一句话目标}}

上下文：
- 项目形态：{{例如纯静态、无构建、无依赖}}
- 相关文件：{{路径}}
- 数据结构：{{字段列表，不得改动}}

验收标准：
1. {{可观察的行为}}
2. {{边界情况}}
3. 不得破坏：{{既有行为}}

约束：
- 不新增依赖
- 改动限制在 {{文件}}
- 先给实现计划（不超过 5 步），我确认后再写代码
```

## 3.5 调试

关键在**禁止它直接给修复方案**。先复现，再假设，最后才是改。

```text
现象：{{可观察到的异常，带上具体输入与输出}}
复现：{{步骤}}
已知：{{浏览器/系统、是否稳定、最近改动}}

要求：
1. 先写一个能稳定复现的最小脚本，不要先给修复方案
2. 列出 3 个最可能的假设，按"验证成本"从低到高排序
3. 每次只改一个变量验证，记录结果

输出表格：假设 / 验证方法 / 预期结果 / 实际结果
```

## 3.6 代码评审

关键在**只找问题不改代码**，否则它会顺手重写，你反而看不清原来的毛病。

```text
评审 {{文件}} 中的 {{函数或模块}}。

只找问题，不要改代码：
1. 哪些输入会让它出错或静默失败
2. 哪些状态组合没被处理（空数组、重复点击、网络失败）
3. 哪些地方看似正确但依赖了环境（时区、缓存、编码）
4. 有没有硬编码、密钥、调试残留

输出表格：位置 / 问题 / 触发条件 / 严重程度
不要提风格建议，不要重写代码。
```

## 3.7 生成测试用例

关键在**期望必须具体到字段值**。写“正确解析”等于没写。

```text
为 {{功能}} 生成回归用例。

输入范围：{{真实语料或场景}}
覆盖维度：正常、边界、异常、模糊

输出 Markdown 表：
| 输入 | 期望输出 | 属于哪类 | 为什么值得测 |

要求：
- 20 条以内
- 期望必须具体到字段值，不要写"正确解析"
- 不要解释，不要总结
```

# 附：两条经验

**① 先让"哪一版"可回答，再谈功能。**
纯前端项目最常见的坑不是写错代码，是"你看到的是旧版本"。版本号 + 构建号 + 提交粒度，三件事加起来不到半小时，能省掉大量误判。

**② 把边界写进产品，而不是藏进心里。**
「一句话没标点拆不开」「跨时区会错」「导出是快照」——这些不是缺陷，是这一版的边界。写进 README、做成界面提示，比在演示时被问住要好。
